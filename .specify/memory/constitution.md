# Конституция проекта «it_is_wensday_my_dude»

## Преамбула

Этот проект имеет двойную цель. Первично — отработка agentic-разработки и spec-driven development (SDD) с Claude Code как переносимого на рабочие задачи навыка. Вторично, но не менее реально — сама игра: пиксельная браузерная история про лягушку из мема «it's wednesday my dude», с геймплейным референсом на офлайн-динозавра Chrome.

Из этого следует правило для всех последующих фаз (`/plan-feature`, `/tasks`, `/implement`, `/analyze`): при конфликте между «сделать красиво/по всем канонам игровой архитектуры» и «сделать просто и довести SDD-цикл до конца» — приоритет у второго. Игра — полигон для отработки процесса, а не самоцель.

## Принципы

### I. Простота прежде всего (YAGNI)
Никаких абстракций и паттернов «на вырост», типичных для больших игровых движков (ECS, event bus, dependency injection и т.п.), пока конкретная фича их не потребовала. Масштаб проекта — учебный.

### II. Автономный статический фронтенд
Игра — чистый клиент: TypeScript + Vite + HTML5 Canvas, без бэкенда. Собирается в статический бандл, деплоится как есть (GitHub Pages сейчас; VPS/Netlify — позже, без смены архитектуры). Серверные фичи (лидерборды, мультиплеер) — вне рамок, пока явно не согласованы отдельной фичей.

### III. Производительность рендера
Целевые 60 fps. Игровой цикл — `requestAnimationFrame` + delta-time; игровая логика не завязывается на частоту кадров напрямую. Минимизация аллокаций внутри кадра.

### IV. Тестируемость игровой логики
Чистая логика (столкновения, счёт, состояние игры) отделяется от Canvas-рендеринга и DOM, чтобы покрываться юнит-тестами без мока браузерного окружения. Это точка опоры для `/tdd` внутри роли `developer`.

### V. Минимализм инструментария
Дефолты Vite. Никаких тяжёлых фреймворков (React, Vue и т.п.) для canvas-игры — не нужны. Любое отклонение от минимального набора обосновывается в `plan.md` конкретной фичи.

### VI. SDD прежде кода
Любое нетривиальное изменение проходит цикл `constitution → specify → clarify → plan → tasks → implement`. Исключение — однострочные правки (конфиги, опечатки), по аналогии с глобальным правилом CLAUDE.md.

### VII. Базовая консистентность UX
Управление документируется в `README.md`, пиксельные шрифты читаемы, UI-оверлеи (счёт, game over) контрастны, есть пауза. Оговорка: canvas-игра имеет объективные ограничения по доступности (экранные читалки её не видят) — это принимается как данность, а не игнорируется молча.

### VIII. Консистентность пиксель-арт ассетов
Единый размер тайла/спрайт-сетки на весь проект. Конвенция путей к ассетам фиксируется в `plan.md` первой фичи, где ассеты реально появляются, и после этого не меняется без явного пересмотра конституции.

### IX. Разделение ролей
Каждая фаза SDD-процесса выполняется независимым subagent'ом (`analyst`, `architect`, `developer`, `tester`, `reviewer`) со своим контекстом, а не одной персоной в общем потоке. Это особенно важно для `tester` и `reviewer` — они не должны быть предвзяты ходом реализации, которую не видели изнутри.

## Технологические ограничения

- TypeScript в строгом режиме (`strict: true`).
- Рендеринг — Canvas 2D API. WebGL — только с явным обоснованием в `plan.md` конкретной фичи.
- Без серверного состояния и без сетевых вызовов в игровой логике.
- Целевые браузеры — evergreen (актуальные Chrome/Firefox/Edge/Safari), без поддержки устаревших версий.

## Процесс разработки

- Полное описание workflow — в [`docs/sdd-workflow.md`](../../docs/sdd-workflow.md).
- Любая нетривиальная работа — на ветке `feature/...` или `fix/...`, не в `master` напрямую.
- Коммиты — только через `/commit`.
- Поведенческая логика реализуется через TDD (red → green → refactor), см. `/tdd`.
- Git-операции (branch/commit/push/merge) выполняются исключительно в основном потоке (оркестрирующей slash-командой или пользователем), никогда — внутри subagent'ов.

## Governance

- Правки в этот документ вносятся через `/constitution`, не напрямую редактированием файла в обход процесса.
- Версионирование — semver-подобное: MAJOR при удалении/переопределении принципа, MINOR при добавлении нового принципа или раздела, PATCH при уточнении формулировок без изменения смысла.
- Каждый `plan.md` фичи обязан содержать раздел «Constitution Check» — явную сверку технического решения с принципами выше и, если есть отклонение, его обоснование.
