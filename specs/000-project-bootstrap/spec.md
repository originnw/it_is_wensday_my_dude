# Спецификация: Bootstrap проекта (каркас Vite + TypeScript + Canvas с игровым циклом)

**Ветка:** `feature/000-project-bootstrap` · **Статус:** черновик · **Автор роли:** analyst

## Обзор

Это первая фича проекта. Она не добавляет игровую механику, а создаёт минимальный работающий каркас, поверх которого все последующие фичи (лягушка, препятствия, счёт, game over) будут добавляться без необходимости заново решать вопросы инструментария.

После этой фичи должно существовать:
- Установленный проект на Vite + TypeScript, который можно склонировать и запустить.
- HTML-страница с холстом (`<canvas>`), видимым в браузере.
- Игровой цикл на `requestAnimationFrame`, использующий delta-time (время между кадрами), который непрерывно работает, пока страница открыта — без завязки логики на конкретную частоту кадров.
- Рабочий dev/build пайплайн: команда для локальной разработки и команда для продакшн-сборки статического бандла.

Игровой механики (лягушка, препятствия, столкновения, счёт) в этой фиче намеренно нет — это предмет будущих фич.

## Пользовательские сценарии

У этой фичи два адресата: игрок (конечный пользователь игры) и разработчик проекта (человек или агент, который будет добавлять следующие фичи поверх каркаса). Оба важны для acceptance criteria.

- Сценарий 1 (игрок): Как игрок, я хочу открыть страницу игры в браузере и увидеть, что она загрузилась и работает (не белый экран, не ошибка), чтобы понимать, что я на правильном пути и дальше здесь появится сама игра.
- Сценарий 2 (разработчик): Как разработчик проекта, я хочу одной командой поднять локальный dev-сервер с автообновлением и одной командой собрать статический продакшн-бандл, чтобы дальше по SDD-процессу добавлять функциональность фич поверх готового каркаса, не тратя время на настройку окружения каждый раз заново.

## Acceptance Criteria

- **AC-1:** После клонирования репозитория и установки зависимостей выполнение команды локальной разработки (`npm run dev` или её эквивалент) поднимает локальный dev-сервер без ошибок в терминале и печатает адрес, по которому доступна страница в браузере.
- **AC-2:** Открытие адреса dev-сервера в браузере загружает страницу без ошибок в консоли браузера (devtools console пуста от ошибок) и страница содержит `<canvas>`-элемент видимого ненулевого размера.
- **AC-3:** Сразу после загрузки страницы содержимое canvas закрашено видимым образом (не остаётся пустым/прозрачным фоном по умолчанию) — доказательство, что рендер отработал хотя бы один раз.
- **AC-4:** Пока страница открыта и вкладка активна, на canvas непрерывно, кадр за кадром, происходит перерисовка с помощью `requestAnimationFrame` — это наблюдаемо визуально через какой-либо меняющийся во времени элемент на экране (например, счётчик FPS, меняющееся значение таймера, или иной признак того, что цикл не остановился после первого кадра). [NEEDS CLARIFICATION: должен ли этот визуальный индикатор непрерывной работы цикла быть именно счётчиком FPS (что заодно даёт наблюдаемое подтверждение принципа «60 fps» из конституции), или подойдёт любой другой меняющийся элемент — и остаётся ли этот индикатор в продакшн-сборке дальше, или это чисто dev-инструмент, который можно будет убрать/спрятать в следующих фичах?]
- **AC-5:** Игровой цикл вычисляет delta-time (время, прошедшее между текущим и предыдущим кадром) на каждой итерации и не содержит логики, которая напрямую зависела бы от конкретной частоты кадров (например, отсутствуют захардкоженные предположения «кадр = 16.6 мс»).
- **AC-6:** Выполнение команды продакшн-сборки (`npm run build` или её эквивалент) завершается без ошибок и без предупреждений уровня error/type-error и производит статический бандл (набор файлов), не требующий отдельного бэкенда для работы.
- **AC-7:** Открытие собранного продакшн-бандла (например, через `npm run preview` или любой статический HTTP-сервер, отдающий содержимое сборки) в браузере воспроизводит то же наблюдаемое поведение, что и dev-режим: страница загружается без ошибок, canvas виден и закрашен, цикл непрерывно тикает (AC-2–AC-4).
- **AC-8:** TypeScript-компиляция проходит в строгом режиме (`strict: true`) без ошибок типов — это требование зафиксировано в конституции проекта как технологическое ограничение, не является предметом обсуждения этой фичи.
- **AC-9:** На странице и в исходном коде проекта отсутствуют игровые сущности геймплея — нет лягушки/персонажа, нет препятствий, нет счёта очков, нет экрана game over/restart, нет управления вводом (клавиатура/тач). Единственное содержимое экрана — то, что доказывает работу каркаса (закрашенный canvas и индикатор из AC-4).
- **AC-10:** В корне проекта есть `README.md` (или раздел в существующем), описывающий, как установить зависимости, запустить dev-режим и собрать продакшн-бандл — минимум команды из AC-1 и AC-6.

## Не-цели

- Никакой игровой механики: сама лягушка (спрайт, управление, физика прыжка), препятствия, столкновения, счёт очков, экраны победы/поражения — всё это предмет будущих фич, не этой.
- Никаких игровых или пиксель-арт ассетов (спрайты, звук, шрифты) — конвенция ассетов (принцип VIII конституции) фиксируется в `plan.md` той будущей фичи, где ассеты реально появятся впервые, не здесь.
- Никакого деплоя (настройка GitHub Pages, CI/CD-пайплайна публикации) — эта фича только про то, что бандл можно собрать локально; куда и как его публиковать — забота отдельной будущей фичи.
- Никакой адаптивности под мобильные экраны и touch-управление.
- Никакого сохранения состояния (localStorage, лучшие результаты) — не применимо, пока нет самой игры.
- Никакой продакшн-полировки UI/стилей — видимое содержимое минимально и служит только доказательством работы каркаса (AC-3, AC-4), а не финальным визуальным решением игры.
- Не фиксируется структура папок `src/` и внутренняя организация кода — это техническое решение принимает роль `architect` в `plan.md`, не эта спецификация.
- Не решается, нужен ли на этом этапе тестовый раннер / юнит-тесты (см. маркер неоднозначности ниже) — если ответ на маркер будет «нет», это тоже явно останется вне цели этой фичи.
