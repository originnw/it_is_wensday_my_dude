# План реализации: Bootstrap проекта (каркас Vite + TypeScript + Canvas с игровым циклом)

**Ветка:** `feature/000-project-bootstrap` · **Источник:** `spec.md` этой же фичи · **Автор роли:** architect

## Технический подход

### Инструментарий сборки

Стартуем от официального шаблона Vite `vanilla-ts` (`npm create vite@latest . -- --template vanilla-ts`) — это уже даёт `npm run dev` / `npm run build` / `npm run preview` "из коробки" (закрывает AC-1, AC-6, AC-7) и `tsconfig.json` со `strict: true` по умолчанию (закрывает AC-8). Никаких дополнительных сборочных плагинов не добавляется — принцип V («Минимализм инструментария»).

### Структура `src/`

```
index.html
src/
  main.ts            — точка входа: инициализация canvas, запуск игрового цикла
  style.css          — стили: fullscreen canvas, сброс отступов
  game/
    loop.ts          — createGameLoop(): requestAnimationFrame + вычисление delta-time
  render/
    canvas.ts         — setupCanvas(): создание/подгонка canvas под viewport, получение 2D-контекста
  dev/
    fpsCounter.ts      — dev-only FPS-оверлей
```

Структура намеренно плоская, без слоёв «на вырост» (нет `entities/`, `systems/`, `state/` — им пока нечего хранить). Она не является финальной: следующая фича (лягушка/цикл прыжка) вправе её расширить под появившуюся игровую логику, ничего здесь не запрещает пересмотр.

### Fullscreen canvas (AC-2, AC-7)

`render/canvas.ts` создаёт `<canvas>` (или берёт готовый из `index.html`) и один раз при загрузке страницы выставляет `canvas.width = window.innerWidth` и `canvas.height = window.innerHeight` — размер буфера рисования, а не только CSS-размер, чтобы избежать блюра/растяжения растра. CSS (`style.css`) дополнительно даёт `html, body { margin: 0; }` и `canvas { display: block; }`, чтобы не было скроллбаров/отступов браузера по умолчанию.

Согласно «Не-целям» спецификации, обработчик `window.addEventListener('resize', ...)` **не добавляется** — canvas подгоняется под viewport только на момент загрузки, динамический ресайз/адаптивность вне объёма этой фичи.

### Игровой цикл: `requestAnimationFrame` + delta-time (AC-4, AC-5)

`game/loop.ts` экспортирует одну функцию `createGameLoop(callback: (deltaTimeSeconds: number) => void): { start(): void }`. Реализация — замыкание с `let lastTimestamp: number | null`, на каждый тик `requestAnimationFrame(tick)`:

```
deltaTime = lastTimestamp === null ? 0 : (timestamp - lastTimestamp) / 1000  // секунды, не мс
lastTimestamp = timestamp
callback(deltaTime)
requestAnimationFrame(tick)
```

Никаких констант вида «1 кадр = 16.6 мс» — delta-time вычисляется каждый раз из реальных таймстемпов `rAF`, что закрывает AC-5. Браузер сам приостанавливает `rAF` для неактивных/свёрнутых вкладок — отдельная обработка `visibilitychange` не требуется, это и есть смысловое соответствие «пока вкладка активна» из AC-4 без лишнего кода (принцип I).

`main.ts` передаёт в `createGameLoop` коллбэк, который на каждый кадр закрашивает canvas сплошным цветом (`ctx.fillRect(0, 0, canvas.width, canvas.height)`) — это одновременно доказывает первый рендер сразу после загрузки (AC-3) и непрерывную перерисовку кадр за кадром (AC-4). Никакой игровой сущности (спрайт, ввод, счёт) в этом коллбэке нет — AC-9.

Чтобы не аллоцировать объекты каждый кадр (принцип III, «минимизация аллокаций внутри кадра»), `deltaTime` передаётся как примитив (`number`), не оборачивается в объект/структуру.

### FPS-счётчик — только dev (AC-4, AC-7, AC-9)

`dev/fpsCounter.ts` экспортирует `createFpsCounter(): { report(deltaTimeSeconds: number): void }` — считает кадры за последнюю секунду и обновляет текст в `<div>`-оверлее, добавленном в DOM (`position: fixed`, верхний угол, минимальные инлайн-стили — без отдельного CSS-файла ради простоты).

В `main.ts` эта функциональность подключается **условно и через динамический импорт**:

```ts
if (import.meta.env.DEV) {
  const { createFpsCounter } = await import('./dev/fpsCounter');
  const fps = createFpsCounter();
  // fps.report(dt) вызывается внутри игрового цикла
}
```

`import.meta.env.DEV` — статически известный на этапе сборки Vite флаг (`true` в `npm run dev`, `false` после `npm run build`). Динамический импорт под таким статическим условием Vite/Rollup исключает из продакшн-бандла при code-splitting — весь модуль `fpsCounter.ts` физически не попадает в prod-чанк. Это самый простой способ закрыть требование АС-7 («в продакшене FPS-счётчик необязателен») без ручного флага сборки или отдельного entry point — согласуется с принципом V.

### Точка входа `main.ts`

Собирает три модуля вместе: `setupCanvas()` → `createFpsCounter()` (только dev, через динамический импорт) → `createGameLoop(...).start()`. Все зависимости — явные вызовы функций, без DI-контейнера, без event bus (принцип I).

### README (AC-10)

`README.md` в корне получает разделы «Установка», «Разработка» (`npm install`, `npm run dev`), «Сборка» (`npm run build`, `npm run preview`) — минимум команд из AC-1 и AC-6.

## Constitution Check

| Принцип | Соответствие / отклонение |
|---|---|
| I. Простота прежде всего (YAGNI) | Соответствие. Три плоских модуля (`loop.ts`, `canvas.ts`, `fpsCounter.ts`) без ECS/event bus/DI. Обработчик resize сознательно не добавлен, т.к. не требуется спецификацией. |
| II. Автономный статический фронтенд | Соответствие. Vite + TS, статический бандл через `npm run build`, без бэкенда и сетевых вызовов. |
| III. Производительность рендера | Соответствие. `rAF` + delta-time как примитив (без аллокаций объектов на кадр). Цель 60 fps наблюдаема через dev-only FPS-счётчик (AC-4). |
| IV. Тестируемость игровой логики | Не применим в этой фиче — игровой логики (столкновения, счёт) ещё нет (см. «Не-цели» spec.md). Настройка тестового раннера явно отложена явным решением В2. Отмечено как риск ниже — на будущее `loop.ts` уже написан в виде чистой функции без побочных эффектов на верхнем уровне, что упростит покрытие тестами, когда раннер появится. |
| V. Минимализм инструментария | Соответствие. Дефолтный шаблон Vite `vanilla-ts`, ни одного дополнительного фреймворка/библиотеки (FPS-счётчик — самописный `<div>`, не `stats.js`). |
| VI. SDD прежде кода | Соответствие — эта фича проходит полный цикл `specify → clarify → plan → tasks → implement`. |
| VII. Базовая консистентность UX | Частично применим. `README.md` документирует команды запуска (AC-10). Управление вводом, пауза, UI-оверлеи игры — не применимы, т.к. в этой фиче нет геймплея (AC-9); станут актуальны в фичах, где появится реальное управление. |
| VIII. Консистентность пиксель-арт ассетов | Не применим — фича явно не вводит ассеты («Не-цели» spec.md). Конвенция путей будет зафиксирована в `plan.md` первой фичи с реальными ассетами. |
| IX. Разделение ролей | Соответствие на уровне процесса — этот план готовит `architect`, реализацию будет вести `developer`, ревью — `reviewer`, независимо друг от друга. |

Отклонений от конституции нет.

## Риски и открытые вопросы

- **Tree-shaking FPS-счётчика.** Ожидание, что динамический импорт под `import.meta.env.DEV` исключит `fpsCounter.ts` из prod-бандла, — стандартное поведение Vite/Rollup, но это не hard-требование AC-7 (там сказано «необязателен», не «обязан отсутствовать»). Если в `/implement` окажется, что code-splitting не сработал как ожидалось (например, чанк всё равно грузится), это не блокер приёмки — достаточно, что счётчик не отображается/не вызывается в проде.
- **Отсутствие тестового раннера.** Принцип IV конституции пока не применим — как только появится первая тестируемая логика (будущая фича), `loop.ts` и `canvas.ts` в их нынешнем виде (чистые функции, минимум побочных эффектов на верхнем уровне модуля) должны быть достаточно тестируемыми без дополнительного рефакторинга; это стоит перепроверить в `plan.md` той фичи.
- **Место `<canvas>`: в `index.html` статически или создаётся в `main.ts` рантаймом.** Обе реализации закрывают все AC одинаково — оставлено на усмотрение `developer` в `/tasks`, не является архитектурным решением, требующим фиксации здесь.
