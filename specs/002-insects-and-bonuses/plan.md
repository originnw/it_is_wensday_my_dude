# План реализации: Насекомые и бонусы

**Ветка:** `feature/002-insects-and-bonuses` · **Источник:** `spec.md` этой же фичи · **Автор роли:** architect

## Технический подход

### Обзор архитектуры

Пять новых чистых модулей `game/*` поверх уже реализованных `game/frog.ts`/`game/input.ts` (`001-frog-movement`), плюс два новых модуля рендера и точечный рефакторинг существующих `game/frog.ts`/`render/frog.ts`. Структура остаётся плоской (принцип I) — ни ECS, ни event bus, ни реестра типов сущностей (явная «Не-цель» spec.md): два вида насекомых и два знака бонусов заданы напрямую как union-типы (`'mosquito' | 'dragonfly'`, `'positive' | 'negative'`), без механизма регистрации будущих типов.

```
src/
  game/
    frog.ts        — БЕЗ ИЗМЕНЕНИЙ логики; ДОБАВЛЯЕТСЯ getFrogRect() + переносится
                      сюда FROG_CROUCH_HEIGHT_MULTIPLIER (был в render/frog.ts)
    geometry.ts     — Rect, rectsIntersect() — общий AABB-тест (AC-5, AC-8)
    geometry.test.ts
    insects.ts      — InsectsState, spawnInsect(), updateInsects() (AC-1–AC-4, AC-6)
    insects.test.ts
    bonuses.ts      — BonusesState, spawnBonus(), updateBonuses() (AC-7, AC-9)
    bonuses.test.ts
    effects.ts      — BonusEffectState, applyBonusEffect(), tickEffect(),
                      insectSpeedMultiplier() (AC-10–AC-13)
    effects.test.ts
    world.ts         — WorldState, createWorldState(), updateWorld():
                      оркестрация + разрешение столкновений (AC-5, AC-6, AC-8, AC-14)
    world.test.ts
  render/
    frog.ts         — рефакторится: y/height считаются через getFrogRect()
    insects.ts       — drawInsects() — плейсхолдер-фигуры по типу
    bonuses.ts       — drawBonuses() — плейсхолдер-фигуры, цвет по знаку (AC-17)
  main.ts            — createFrogState/updateFrog заменяются на createWorldState/updateWorld;
                      добавляются вызовы drawInsects/drawBonuses
```

Разделение «чистая логика / рендер» повторяет прецедент `001-frog-movement` (принцип IV, AC-16 этой фичи): все новые файлы `game/*.ts` не импортируют ничего из DOM/Canvas API, принимают только примитивы и объекты состояния — тестируемы в Vitest-окружении `node` без `jsdom` (тестовый раннер и конфигурация уже есть, новых зависимостей эта фича не добавляет).

### Общая модель координат

Как и `FrogState.x`, все новые сущности используют абсолютные px-координаты canvas: `x`/`y` — левый верхний угол ограничивающего прямоугольника, `y` растёт вниз. В отличие от `frog.ts` (которому вертикаль не нужна — там она выражена через `jumpOffsetY` относительно внешнего `groundY`), логике насекомых и бонусов вертикаль нужна напрямую (падение сверху, выход через нижний край) — поэтому `updateInsects`/`updateBonuses` принимают `worldWidth`, `worldHeight` и `groundY` явными параметрами, по аналогии с тем, как `updateFrog` уже принимает `worldWidth`. Ни один из этих модулей не хранит и не кэширует размеры canvas у себя — они приходят из `main.ts` каждый кадр, как и раньше.

### `game/geometry.ts` — общий AABB-тест (закрывает инфраструктуру AC-5, AC-8)

```ts
export interface Rect { x: number; y: number; width: number; height: number; }
export function rectsIntersect(a: Rect, b: Rect): boolean;
```

Стандартный тест пересечения прямоугольников по осям. Переиспользуется и для «лягушка × насекомое» (AC-5), и для «лягушка × бонус» (AC-8) — единственный источник истины для геометрии столкновений, без дублирования формулы.

### `game/frog.ts` — точечное расширение (без изменения существующей логики `updateFrog`)

Добавляется:

```ts
export const FROG_CROUCH_HEIGHT_MULTIPLIER = 0.5; // перенесено из render/frog.ts
export function getFrogRect(state: FrogState, groundY: number): Rect;
```

**Почему перенос, а не дублирование.** До этой фичи высота лягушки в присевшей позе (`FROG_HEIGHT_PX * 0.5`) вычислялась только в `render/frog.ts` — этого было достаточно, пока константа нужна была только для рисования. AC-5/AC-8 требуют «прямоугольную зону тела лягушки в её текущем визуальном состоянии» для проверки столкновений — то есть **тот же** прямоугольник, что рисуется, должен быть доступен чистой логике (`game/world.ts`), которая не может импортировать `render/*` (запрет на зависимость логики от рендера, принцип IV). Решение — поднять формулу на уровень `game/frog.ts` (`getFrogRect`) как единственный источник истины; `render/frog.ts` переиспользует её же вместо повторного вычисления `y`/`height`. Это рефакторинг существующего файла 001-й фичи, не изменение поведения — `drawFrog` рисует пиксель-в-пиксель то же самое, что и раньше (проверяется тем, что `frog.test.ts` и `quickstart.md` 001-й фичи продолжают проходить без изменений, AC-15).

### `game/insects.ts` — насекомые (AC-1–AC-4, AC-6, AC-3)

```ts
export type InsectType = 'mosquito' | 'dragonfly';
export type InsectEntryPoint = 'top' | 'left' | 'right';

export interface Insect {
  type: InsectType;
  x: number; y: number; width: number; height: number;
  vx: number; vy: number; // базовая скорость (px/s), без учёта текущего множителя бонуса
}

export interface InsectsState {
  list: Insect[];
  spawnTimerSeconds: number;
}

export function createInsectsState(): InsectsState;
export function updateInsects(
  state: InsectsState,
  deltaTimeSeconds: number,
  worldWidth: number,
  worldHeight: number,
  groundY: number,
  speedMultiplier: number,     // из effects.ts, 1 = база (AC-10/AC-11)
  random: () => number = Math.random,
): void;
```

**Спавн (AC-1, AC-3).** `spawnTimerSeconds` отсчитывается каждый кадр; при достижении нуля создаётся насекомое случайного типа (`mosquito`/`dragonfly`, 50/50) и случайной точки входа (`top`/`left`/`right`), таймер сбрасывается на `INSECT_SPAWN_INTERVAL_MIN_S + random() * (MAX - MIN)` (частота — tuning-параметр, «Не-цели» spec.md). Высота появления для `left`/`right` — случайная в диапазоне `[0, JUMP_HEIGHT_PX + FROG_HEIGHT_PX]` px **над землёй** (константы импортируются из `frog.ts`) — этот диапазон **специально сконструирован** так, чтобы включать и зону, достижимую стоя (нижняя часть диапазона, `≤ FROG_HEIGHT_PX`), и зону, достижимую только прыжком (верхняя часть) — прямая реализация AC-3, а не случайное совпадение. Для `top` высота появления не рандомизируется отдельно — насекомое стартует у `y = 0` (верхний край canvas), что автоматически выше зоны прыжка на большинстве размеров экрана, и становится «прыжково-достижимым», а затем «пеше-достижимым» по мере падения — естественная реализация AC-3 без дополнительного кода.

**Движение (AC-2).** Без ускорения — `vx`/`vy` в момент спавна фиксируются как константы для типа/направления и не меняются кадр к кадру (кроме множителя от бонуса, который считается заново каждый кадр, а не «встраивается» в `vx`/`vy` насекомого — см. `effects.ts`, это и даёт мгновенный эффект AC-10/AC-11 на уже летающих насекомых). `left`/`right` — чисто горизонтальное движение (`vy = 0`), «преимущественно горизонтально» удовлетворяется тривиально (100% горизонтали — частный случай «преимущественно»). `top` — чисто вертикальное вниз (`vx = 0`); AC-2 допускает «вертикально либо по диагонали» — выбрана вертикаль как более простой вариант (принцип I), диагональ не добавляет игровой ценности сверх уже достаточной рандомизации через `left`/`right`.

**Выход за край (AC-4).** После применения движения на этом кадре: `left`-насекомое (движется вправо) удаляется при `x > worldWidth`; `right`-насекомое (движется влево) — при `x + width < 0`; `top`-насекомое — при `y > worldHeight`. Удаление — без штрафа, просто исключение из `list`.

**Очки (AC-6).** `MOSQUITO_SCORE = 10`, `DRAGONFLY_SCORE = 25` — экспортируемые константы в `insects.ts`, используются `world.ts` при разрешении столкновений; конкретные числа — tuning-параметр («Не-цели»), важно только `DRAGONFLY_SCORE > MOSQUITO_SCORE`.

**Реализация без аллокаций внутри кадра (принцип III).** Удаление вышедших за край насекомых — обратный проход по `list` с `splice()` по индексу, а не `Array.prototype.filter()`/`map()` — не аллоцирует новый массив каждый кадр, мутирует существующий на месте (по аналогии с тем, как `updateFrog` мутирует `FrogState`). Аллокация нового объекта `Insect` происходит только в момент фактического спавна (редкое событие, не каждый кадр) — неизбежный минимум, не по кадрам.

### `game/bonuses.ts` — бонусы (AC-7, AC-9)

```ts
export type BonusSign = 'positive' | 'negative';
export interface Bonus { sign: BonusSign; x: number; y: number; width: number; height: number; }
export interface BonusesState { list: Bonus[]; spawnTimerSeconds: number; }

export function createBonusesState(): BonusesState;
export function updateBonuses(
  state: BonusesState,
  deltaTimeSeconds: number,
  worldWidth: number,
  worldHeight: number,
  random: () => number = Math.random,
): void;
```

Спавн — по таймеру, аналогично насекомым, но точка появления фиксирована («у верхнего края», AC-7): `x` — случайный в пределах `[0, worldWidth - BONUS_WIDTH_PX]`, `y = 0`, знак — 50/50. Движение — строго вертикально вниз с постоянной скоростью `BONUS_FALL_SPEED_PX_S`, `vx` не существует как поле вовсе (не «`vx = 0`, которое можно было бы случайно изменить», а отсутствие горизонтальной составляющей в самой структуре — AC-7 требует «строго вертикально», это выражено через отсутствие поля, а не проверку значения). Выход за нижний край (`y > worldHeight`) — удаление без применения эффекта и без штрафа/награды (AC-9), тем же паттерном обратного `splice()`, что и в `insects.ts`.

### `game/effects.ts` — эффект бонуса (AC-10–AC-13)

```ts
export interface BonusEffectState { sign: BonusSign | null; remainingSeconds: number; }

export function createEffectState(): BonusEffectState;
export function applyBonusEffect(state: BonusEffectState, sign: BonusSign): void;
export function tickEffect(state: BonusEffectState, deltaTimeSeconds: number): void;
export function insectSpeedMultiplier(state: BonusEffectState): number;
```

**Ключевое архитектурное упрощение (AC-13), стоит зафиксировать явно, чтобы `developer` не реализовал более сложную ветвящуюся логику, чем нужно.** На первый взгляд AC-13 описывает три разных случая («нет активного эффекта» / «тот же знак — продлить» / «противоположный знак — погасить и запустить новый»). При точном прочтении все три случая приводят к **одному и тому же присваиванию**:

```ts
export function applyBonusEffect(state: BonusEffectState, sign: BonusSign): void {
  state.sign = sign;
  state.remainingSeconds = BONUS_EFFECT_DURATION_S;
}
```

- Нет активного эффекта → `sign`/`remainingSeconds` устанавливаются впервые — совпадает.
- Тот же знак → «продлевает, перезапускает отсчёт, не усиливая эффект сверх значения одного бонуса» (spec.md) — то есть `remainingSeconds` просто становится снова полным, `sign` не меняется (переприсвоение того же значения — no-op) — совпадает.
- Противоположный знак → «гасит и сразу запускает новый с полной длительностью» — установка нового `sign`/полного `remainingSeconds` — совпадает.

Никакого `if` по знаку не требуется — ветвление, которое интуитивно ожидается по тексту AC-13, схлопывается в одну строку, потому что во всех трёх случаях результат идентичен. Это не потеря детализации: `state.sign` до вызова нигде не читается внутри `applyBonusEffect`, поэтому логика не может «повести себя иначе» в зависимости от предыдущего значения — что и требуется по AC-13 (сила эффекта не накапливается, никогда не зависит от того, что было раньше). Тесты `effects.test.ts` тем не менее пишутся по всем трём сценариям из AC-13 отдельно (red-green по каждому сценарию), а не полагаются на то, что «раз код простой, тестировать нечего» — упрощение реализации не освобождает от TDD по поведению.

`tickEffect` — `remainingSeconds -= dt`; при `<= 0` → `sign = null`, `remainingSeconds = 0` (AC-12, возврат к базе).

`insectSpeedMultiplier(state)` — `state.sign === null → 1`; `'positive' → BONUS_EFFECT_POSITIVE_SPEED_MULTIPLIER` (< 1, насекомые медленнее); `'negative' → BONUS_EFFECT_NEGATIVE_SPEED_MULTIPLIER` (> 1, быстрее). Возвращаемое число умножает `vx`/`vy` насекомого в `updateInsects` каждый кадр заново (не «запекается» в само насекомое) — именно это и даёт «мгновенно охватывает уже находящихся в кадре насекомых» из AC-10/AC-11: как только `state.sign` меняется, на следующем же вызове `updateInsects` **все** насекомые в `list` (включая уже летавшие до этого) получают новую эффективную скорость.

**Сознательное упрощение «скорость и/или высота» (AC-10/AC-11).** Спецификация допускает эффект через скорость, через высоту полёта, либо через оба параметра сразу («и/или»). План реализует эффект **только через скорость** (`insectSpeedMultiplier`), не трогая высоту появления насекомых. Это осознанно выбранная, явно разрешённая спецификацией часть «или» — динамическое изменение уже закреплённой на спавне высоты полёта существующих насекомых потребовало бы либо телепортации их `y` (визуально дёрганое поведение, хуже для UX), либо отдельного механизма плавной интерполяции высоты (сложность без прямого требования AC — принцип I). Изменение скорости уже полностью удовлетворяет качественному критерию AC-10/AC-11 («легче/сложнее ловить») и не создаёт визуальных артефактов.

### `game/world.ts` — оркестрация и столкновения (AC-5, AC-6, AC-8, AC-14, AC-15)

```ts
export interface WorldState {
  frog: FrogState;
  insects: InsectsState;
  bonuses: BonusesState;
  effect: BonusEffectState;
  score: number;
}

export function createWorldState(worldWidth: number): WorldState;

export function updateWorld(
  state: WorldState,
  input: FrogInput,
  deltaTimeSeconds: number,
  worldWidth: number,
  worldHeight: number,
  groundY: number,
  random: () => number = Math.random,
): void;

// Экспортируются отдельно для точечного юнит-тестирования (принцип IV):
export function resolveBonusCollisions(frogRect: Rect, bonuses: BonusesState, effect: BonusEffectState): void;
export function resolveInsectCollisions(frogRect: Rect, insects: InsectsState): number; // возвращает набранные очки
```

Столкновения «лягушка × что-то» неизбежно требуют знания и о лягушке, и о цели одновременно — поэтому это код `world.ts`, а не `insects.ts`/`bonuses.ts`/`frog.ts` по отдельности (ни один из них не должен знать о существовании двух других — принцип I, каждый модуль отвечает за одну сущность).

**Порядок вычислений внутри одного вызова `updateWorld` — важен, фиксируется явно (чтобы не стать неожиданной находкой `reviewer` на `/analyze`, как это уже было в `001-frog-movement`):**

1. `updateFrog(state.frog, input, dt, worldWidth)` — без изменений, поведение 001-й фичи не трогается (AC-15).
2. `updateBonuses(state.bonuses, dt, worldWidth, worldHeight, random)` — бонусы двигаются **до** проверки столкновений с ними.
3. `frogRect = getFrogRect(state.frog, groundY)` — прямоугольник лягушки в её состоянии **этого** кадра, вычисляется один раз и переиспользуется на шагах 4 и 6 (лягушка между ними не двигается).
4. `resolveBonusCollisions(frogRect, state.bonuses, state.effect)` — проглоченные бонусы удаляются из `list`, `applyBonusEffect` вызывается для каждого попадания.
5. `multiplier = insectSpeedMultiplier(state.effect)` — читается **после** шага 4, а не до него.
6. `updateInsects(state.insects, dt, worldWidth, worldHeight, groundY, multiplier, random)` — насекомые двигаются с учётом множителя, который мог измениться только что, на этом же кадре.
7. `state.score += resolveInsectCollisions(frogRect, state.insects)`.
8. `tickEffect(state.effect, dt)` — длительность эффекта уменьшается **в конце** кадра.

**Почему бонусы обрабатываются раньше насекомых, а не наоборот или параллельно.** Это единственный порядок, при котором бонус, пойманный именно на этом кадре, успевает повлиять на движение насекомых **этого же** кадра (шаг 6), а не только следующего — прямая, буквальная реализация «эффект применяется мгновенно» (AC-10/AC-11), а не «мгновенно с точностью до одного кадра (~16 мс)». Обратный порядок (насекомые двигаются раньше бонусов) тоже прошёл бы приёмку по AC (задержка в один кадр практически неотличима на глаз), но выбранный порядок точнее соответствует тексту AC и не требует отдельного обоснования «одного кадра достаточно».

**Множественные одновременные попадания.** Ни AC-5, ни AC-8 не ограничивают число объектов, которые лягушка может задеть за один кадр — `resolveInsectCollisions`/`resolveBonusCollisions` проходят по **всему** списку и обрабатывают каждое пересечение, а не останавливаются на первом. Для насекомых это очевидно корректно (очки суммируются). Для бонусов при гипотетическом одновременном попадании двух бонусов противоположного знака на одном кадре результат определяется порядком обхода массива (последний обработанный бонус «побеждает») — крайне маловероятный edge case (два бонуса должны занимать пересекающиеся координаты в момент поимки), явно не описанный в spec.md; принято как допустимое детерминированное (хоть и порядко-зависимое) поведение, см. «Риски».

### `render/insects.ts` / `render/bonuses.ts` — отрисовка (плейсхолдеры, «Не-цели» spec.md)

`drawInsects(ctx, insects: Insect[])` — прямоугольники-плейсхолдеры, различимые по типу (AC-1: «минимум два различимых типа») размером/цветом: комар — маленький серый прямоугольник, стрекоза — крупнее и другого цвета (например, бирюзового). Никакой анимации/спрайтов — вне объёма.

`drawBonuses(ctx, bonuses: Bonus[])` — плейсхолдер-круг (`ctx.arc`) постоянной формы, цвет зависит от `sign`: `positive` — зелёный, `negative` — красный. Это закрывает AC-17 («визуально различим ещё до поимки») минимальным способом — одна форма, два цвета, без дополнительной геометрии.

### Связывание в `main.ts`

`createFrogState(canvas.width)` + `updateFrog(...)` заменяются на `createWorldState(canvas.width)` + `updateWorld(worldState, input.read(), dt, canvas.width, canvas.height, groundY)`. После апдейта — `drawFrog(ctx, worldState.frog, groundY)`, затем `drawInsects(ctx, worldState.insects.list)`, `drawBonuses(ctx, worldState.bonuses.list)`. `random` не передаётся явно из `main.ts` (используется дефолт `Math.random` из сигнатуры `updateWorld`) — инъекция `random` существует исключительно ради тестируемости `insects.test.ts`/`bonuses.test.ts`/`world.test.ts` с детерминированной последовательностью значений, а не как продуктовая необходимость (принцип I — параметр с дефолтом, а не отдельный слой конфигурации).

**Диагностика счёта только для dev-сборки.** Счёт — внутреннее поле (AC-14, «Не-цели»: HUD вне объёма), но его отсутствие на экране усложнило бы ручную проверку AC-6/AC-14 в `quickstart.md`. Добавляется `if (import.meta.env.DEV && worldState.score !== previousScore) console.log('score:', worldState.score)` в `main.ts` рядом с уже существующим dev-only `fps`-блоком (тот же паттерн: код, который не попадает в прод-бандл). Это не UI/HUD-элемент (не рисуется на canvas, не видим игроку в проде) — не нарушает «Не-цели» о запрете HUD, а лишь даёт `tester`-у инструмент проверки без визуализации счёта на экране.

## Риски и открытые вопросы

- **Точные числовые tuning-параметры** (скорости насекомых/бонусов, очки за тип, диапазон высот появления, длительность и сила эффекта бонуса, интервалы спавна) — рабочие дефолты подбираются `developer`/`tester` в `/implement` по ощущениям от плейтеста; spec.md явно не фиксирует их как продуктовое требование («Не-цели»), аналогично числовым константам `001-frog-movement`.
- **Порядок «бонусы раньше насекомых» внутри `updateWorld`.** Зафиксирован явно в этом плане (см. §`game/world.ts`) именно затем, чтобы не стать «находкой `reviewer`» при `/analyze`, как это произошло с каскадным порядком прыжка в `001-frog-movement`. Альтернативный порядок (насекомые раньше бонусов) тоже был бы приёмочно корректен — расхождение всего в один кадр (~16 мс), неразличимое на глаз — но выбранный порядок точнее соответствует буквальному «мгновенно» из AC-10/AC-11.
- **Одновременное попадание двух бонусов противоположного знака в один и тот же кадр.** Не описано в spec.md явно; в этом плане принято детерминированное, но порядко-зависимое поведение («последний по порядку обхода массива побеждает») — см. §`game/world.ts`. Вероятность события крайне мала (совпадение координат двух независимо падающих объектов в момент поимки), риска для приёмки AC не несёт, но стоит держать в уме, если `tester` попытается специально это воспроизвести в `quickstart.md`.
- **Эффект бонуса реализован только через скорость, не через высоту полёта.** Явно разрешённая спецификацией альтернатива («и/или», AC-10/AC-11) — обоснование в §`game/effects.ts`. Если при плейтесте ощущение «легче/сложнее ловить» окажется недостаточно выраженным только за счёт скорости, `developer`/`tester` вправе усилить величину `BONUS_EFFECT_*_SPEED_MULTIPLIER` (tuning), не пересматривая план.
- **`getFrogRect()` — рефакторинг файла из `001-frog-movement`.** Риск регресса визуального поведения лягушки минимален (формула переносится, не переписывается), но `tester` должен перепройти пункты 1–13 `quickstart.md` `001-frog-movement` в рамках приёмки этой фичи (AC-15 требует явно), а не полагаться только на то, что тесты `frog.test.ts` остаются зелёными.
