# План реализации: Управление лягушкой (перемещение, прыжки, приседание)

**Ветка:** `feature/001-frog-movement` · **Источник:** `spec.md` этой же фичи · **Автор роли:** architect

## Технический подход

### Обзор архитектуры

Три новых модуля поверх каркаса `000-project-bootstrap`, с чётким разделением «чистая логика / DOM-ввод / рендер» (принцип IV конституции, AC-12):

```
src/
  game/
    loop.ts          — без изменений (000-project-bootstrap)
    input.ts          — createInputTracker(): чтение клавиатуры (DOM, побочные эффекты)
    frog.ts            — createFrogState(), updateFrog(): чистая логика позиции/состояний (AC-12)
    frog.test.ts       — юнит-тесты updateFrog() (Vitest, без DOM/canvas)
  render/
    canvas.ts          — без изменений
    frog.ts            — drawFrog(): отрисовка лягушки на основе FrogState
  main.ts              — обновляется: связывает input → updateFrog → drawFrog внутри цикла
README.md              — раздел «Управление» (AC-13)
```

Структура остаётся плоской (принцип I, YAGNI) — ни ECS, ни отдельного слоя «entities/systems», ни event bus. Три функции связываются прямыми вызовами в `main.ts`, как и в `000-project-bootstrap`.

### Тестовый раннер: Vitest (новая зависимость)

AC-12 требует юнит-тестируемую логику без эмуляции браузера — в проекте пока нет тестового раннера (риск, явно оставленный открытым в `plan.md` `000-project-bootstrap`: «как только появится первая тестируемая логика — это стоит перепроверить»). Она появилась в этой фиче, поэтому раннер добавляется сейчас.

Выбор — **Vitest**: нативный компаньон Vite (тот же движок трансформации/резолвинга модулей, конфиг подключается через существующий `vite.config.ts` без отдельного бандлера), окружение по умолчанию — `node` (не `jsdom`), чего достаточно, поскольку `frog.ts` не трогает DOM/canvas — это и есть смысл AC-12. Никакой альтернативы, требующей отдельного бандлера/транспайлера (Jest и его конфигурация под ESM/Vite) не привлекается — принцип V («минимализм инструментария»): при уже имеющемся Vite это минимальное добавление, а не новый инструмент со своей экосистемой.

`package.json` получает `"test": "vitest run"` и `devDependency` `vitest`. Тестовые файлы располагаются рядом с исходником (`src/game/frog.test.ts`), без отдельной директории `tests/` — меньше структурных решений на пустом месте.

### `game/frog.ts` — чистая логика (закрывает AC-1–AC-11, AC-14 логически, AC-12 архитектурно)

Состояние:

```ts
interface FrogState {
  x: number;              // левый край, px, абсолютные координаты canvas
  isAirborne: boolean;
  jumpElapsedSeconds: number;
  jumpOffsetY: number;     // 0 = на земле; вычисляется каждый update, читается рендером
  activeJumpHeightPx: number; // высота параболы текущего прыжка; решается один раз на старте прыжка (AC-14 — выше при старте из приседа), не меняется до приземления
  isCrouching: boolean;
}

interface FrogInput {
  moveLeft: boolean;
  moveRight: boolean;
  crouch: boolean;
  jumpRequested: boolean;  // one-shot: true только на кадре нажатия пробела
}
```

`updateFrog(state: FrogState, input: FrogInput, deltaTimeSeconds: number, worldWidth: number): void` — мутирует `state` на месте (не аллоцирует новый объект каждый кадр — принцип III, по аналогии с тем, как `deltaTime` уже передаётся примитивом в `loop.ts`). Порядок вычислений внутри одного вызова:

1. **Горизонталь (AC-1–AC-4, AC-9).** `direction = (moveRight ? 1 : 0) - (moveLeft ? 1 : 0)` — одновременное зажатие обеих стрелок даёт `0` без отдельной ветки условия (закрывает AC-4 без отслеживания порядка нажатий, как и зафиксировано в Clarifications spec.md). `x += direction * FROG_SPEED_PX_S * deltaTimeSeconds`, затем `clamp(x, 0, worldWidth - FROG_WIDTH_PX)` — упор в край экрана без телепорта/скролла (AC-3). Логика применяется одинаково независимо от `isAirborne` — то есть без специальной ветки для «в воздухе»: это прямая реализация AC-9 и одновременно закрывает горизонтальную составляющую AC-8 (боковой прыжок = обычное горизонтальное движение AC-1–AC-3, продолжающееся, пока лягушка в воздухе, плюс вертикальная дуга ниже). Отдельного «направления, зафиксированного в момент прыжка» как самостоятельного механизма нет — оно не нужно, потому что стрелки и так продолжают управлять горизонталью весь полёт (AC-9), что делает AC-8 частным случаем уже описанного поведения, а не отдельным кодовым путём. Эта унификация — сознательное упрощение (принцип I), обоснование дано в Clarifications AC-9 spec.md.
2. **Прыжок (AC-5–AC-9, AC-14).** Порядок вычислений в одном вызове `updateFrog` — **каскадный, а не `else if`**: старт прыжка и продолжение полёта проверяются двумя последовательными независимыми `if` внутри одного и того же вызова, а не как взаимоисключающие ветки одного условия. Явная фиксация этого выбора (снимает неоднозначность, найденную `reviewer` при `/analyze`):
   - **а) Старт.** Если `input.jumpRequested && !state.isAirborne` → `isAirborne = true`, `jumpElapsedSeconds = 0`. Условие **намеренно не проверяет `state.isCrouching`** — это прямая реализация AC-14: приседание не блокирует нажатие пробела, прыжок стартует независимо от того, было лягушка присевшей или нет. Одновременно с этим присваивается `activeJumpHeightPx = state.isCrouching ? JUMP_HEIGHT_PX * CROUCH_JUMP_HEIGHT_MULTIPLIER : JUMP_HEIGHT_PX` — решение о высоте прыжка принимается **один раз, здесь, на кадре старта**, по значению `isCrouching`, каким оно было к началу этого вызова `updateFrog` (то есть по результату предыдущего кадра), и не пересчитывается динамически до конца этого прыжка. Пересчитывать нечего: в этом же вызове чуть ниже (шаг 3) `isCrouching` будет пересчитан заново и станет `false`, так как `isAirborne` уже `true` — а пока `isAirborne === true`, `isCrouching` по AC-11 не может снова стать `true` (приседание недоступно в воздухе), так что отпускание/зажатие Ctrl в полёте на `activeJumpHeightPx` уже никак повлиять не может.
   - **б) Продолжение/приземление.** Затем (тем же вызовом — если старт произошёл в шаге «а» выше, это **тот же кадр**, а не следующий) — если `isAirborne` → `jumpElapsedSeconds += deltaTimeSeconds`. Это и есть каскадное поведение: на кадре старта прыжка `jumpElapsedSeconds` по итогу вызова окажется равен `deltaTimeSeconds`, а не строго `0` — второй `if` не пропускается на кадре старта, `else`/отдельного флага «прыжок только что начался» нет. Выбор в пользу каскада, а не `else if` (при котором старт и первый кадр полёта были бы разнесены на два разных вызова `updateFrog`) — сознательное упрощение: одна функция, без дополнительного состояния «прыжок только что начался в этом кадре». Ни на один AC это не влияет: при 60 fps `deltaTimeSeconds` на кадре старта ничтожно мал относительно `JUMP_DURATION_S = 0.5` с, а `jumpOffsetY` на этом кадре будет чуть больше нуля, а не строго ноль — ни один AC не требует, чтобы прыжок стартовал с `jumpOffsetY === 0` именно на первом кадре (AC-5/AC-6 требуют только возврата к `0` к концу дуги и независимости от FPS в сумме, что каскад не нарушает).
   - Если `jumpElapsedSeconds >= JUMP_DURATION_S` → приземление: `isAirborne = false`, `jumpElapsedSeconds = 0`, `jumpOffsetY = 0`. Иначе `jumpOffsetY` считается по параболе, параметризованной долей пройденного времени (а не накоплением скорости/ускорения через Эйлерово интегрирование), с использованием `activeJumpHeightPx`, зафиксированного на старте (а не всегда `JUMP_HEIGHT_PX` — см. AC-14): `fraction = jumpElapsedSeconds / JUMP_DURATION_S; jumpOffsetY = 4 * activeJumpHeightPx * fraction * (1 - fraction)`. Этот вид параболы гарантированно возвращает `jumpOffsetY` к `0` ровно к моменту `fraction = 1` независимо от кадровой частоты (AC-6 — расчёт зависит только от накопленного `deltaTime`, не от числа кадров) и не накапливает численную ошибку по сравнению с итеративным суммированием скорости кадр за кадром — исходная позиция по вертикали гарантированно восстанавливается (AC-5), одинаково и для обычного прыжка, и для прыжка из приседа с увеличенным `activeJumpHeightPx` (AC-14).
3. **Приседание (AC-10, AC-11).** `isCrouching = input.crouch && !isAirborne` — вычисляется заново каждый кадр, без отдельного стейта перехода; вход/выход мгновенны по нажатию/отпусканию Left Ctrl (AC-10) и автоматически недоступны в воздухе (AC-11), совместимы с горизонтальным движением, так как не участвуют в его вычислении (AC-11). Побочный эффект этой же строки — переход «присела → в воздухе» (AC-14): как только шаг 2 установил `isAirborne = true` в кадре старта прыжка, этот шаг в том же кадре пересчитывает `isCrouching` в `false` без какого-либо дополнительного кода — состояния Crouching и Airborne взаимоисключающие уже в силу существующей формулы, а не отдельного перехода, который нужно было бы реализовывать заново.

`FROG_SPEED_PX_S`, `JUMP_DURATION_S`, `JUMP_HEIGHT_PX`, `CROUCH_JUMP_HEIGHT_MULTIPLIER`, `FROG_WIDTH_PX`, `FROG_HEIGHT_PX` — именованные константы в `frog.ts` с рабочими дефолтами (`FROG_SPEED_PX_S = 240`, `JUMP_DURATION_S = 0.5`, `JUMP_HEIGHT_PX = 120`, `CROUCH_JUMP_HEIGHT_MULTIPLIER = 1.5`, `FROG_WIDTH_PX = 32`, `FROG_HEIGHT_PX = 32`). Это tuning-параметры, не зафиксированные спецификацией как продуктовое требование («Не-цели» spec.md) — `developer`/`tester` вправе скорректировать их в `/implement` по ощущениям от плейтеста, не нарушая ни один AC.

### `game/input.ts` — DOM-ввод (impure)

`createInputTracker(): { read(): FrogInput }`. Внутри — замыкание с булевыми флагами `moveLeft`/`moveRight`/`crouch` и одноразовым `jumpRequestedFlag`, обновляемыми через `window.addEventListener('keydown'|'keyup', ...)` по `event.code`:

- `ArrowLeft` → `moveLeft`, `ArrowRight` → `moveRight` (не `event.key`, чтобы не зависеть от раскладки клавиатуры).
- `Space` → на `keydown` с `!event.repeat` выставляет `jumpRequestedFlag = true` (игнорирование `event.repeat` — не даёт автоповтору ОС наплодить лишние срабатывания; сама защита от двойного прыжка всё равно на уровне `updateFrog`/AC-7) и вызывает `event.preventDefault()` (иначе браузер проскроллит страницу пробелом).
- `ControlLeft` → `crouch`. Намеренно **не** `ControlRight`/`Control` в целом — spec.md явно называет «Left Ctrl», а не Ctrl в общем виде (AC-10), и «Не-цели» явно исключают недокументированные альтернативные клавиши.

`read()` возвращает снимок `FrogInput` и сбрасывает `jumpRequestedFlag` в `false` (one-shot consume) — это и даёт API, которое `updateFrog` видит как «пробел нажат в этом кадре», без утечки состояния «нажатие» на последующие кадры.

### `render/frog.ts` — отрисовка

`drawFrog(ctx: CanvasRenderingContext2D, state: FrogState, groundY: number): void` — рисует прямоугольник-плейсхолдер (`ctx.fillRect`) шириной `FROG_WIDTH_PX`, с высотой `FROG_HEIGHT_PX` (обычное состояние) либо уменьшенной (например, `FROG_HEIGHT_PX / 2`) и другим цветом, когда `state.isCrouching` — визуально отличимая присевшая поза (AC-10), без какого-либо конкретного спрайта/анимации (явно вне объёма — «Не-цели» spec.md). Y-позиция считается как `groundY - state.jumpOffsetY - FROG_HEIGHT_PX` (или уменьшенной высоты при приседании), где `groundY` — константа-отступ от низа canvas, вычисляемая в `main.ts` при связывании модулей (не хранится в `FrogState`, чтобы логика оставалась независимой от размеров canvas по вертикали — по AC-3 требуются только горизонтальные границы).

### Связывание в `main.ts`

Заменяет текущий безусловный `ctx.fillRect(...)` на: `input.read()` → `updateFrog(state, input, dt, canvas.width)` → очистка фона (тот же `fillRect` цветом фона) → `drawFrog(ctx, state, groundY)`. Никакого DI-контейнера/event bus — прямые вызовы, как и в `000-project-bootstrap` (принцип I).

### README (AC-13)

Новый раздел «Управление»: таблица/список — стрелка влево/вправо (движение), пробел (прыжок вверх; в сочетании со стрелкой — боковой прыжок; во время приседания — тоже разрешён и выше обычного, AC-14), Left Ctrl (присесть).

## Constitution Check

| Принцип | Соответствие / отклонение |
|---|---|
| I. Простота прежде всего (YAGNI) | Соответствие. Три плоских модуля (`input.ts`, `frog.ts`, `render/frog.ts`), без ECS/event bus/DI. AC-8 сознательно не реализован отдельным кодовым путём — переиспользует горизонтальную логику AC-9, что убирает лишнее состояние «направление на момент прыжка». AC-14 аналогично не вводит отдельный переход/код-путь — переиспользует существующее условие старта прыжка (не добавляя проверку `isCrouching` как блокировку) и добавляет одну новую константу-множитель (`CROUCH_JUMP_HEIGHT_MULTIPLIER`) и одно поле состояния (`activeJumpHeightPx`), без нового state-machine перехода, реализуемого вручную. |
| II. Автономный статический фронтенд | Соответствие. Никаких сетевых вызовов, только клиентская логика и `window`-события клавиатуры. |

| VII. Базовая консистентность UX | Частично применим. Управление документируется в `README.md` (AC-13). Пауза/UI-оверлеи не применимы — в фиче нет ни очков, ни game over («Не-цели» spec.md); требование «есть пауза» из принципа VII — свойство итоговой игры в целом, а не обязательный элемент каждой отдельной фичи, и явно не входит в объём (аналогично трактовке в `plan.md` `000-project-bootstrap`). |

Отклонений от конституции нет; единственное новое обстоятельство — добавление Vitest, обосновано выше как минимально необходимое для соблюдения самого принципа IV, а не как избыточность.

## Риски и открытые вопросы

- **Точные числовые значения tuning-параметров** (`FROG_SPEED_PX_S`, `JUMP_DURATION_S`, `JUMP_HEIGHT_PX`, `CROUCH_JUMP_HEIGHT_MULTIPLIER`, размеры лягушки) — рабочие дефолты подобраны на глаз в этом плане; spec.md явно не фиксирует их как продуктовое требование («Не-цели», включая величину увеличения высоты прыжка из приседа — AC-14). `developer`/`tester` вправе скорректировать значения в `/implement` по результатам ручной проверки (см. `quickstart.md`), не считая это отклонением от плана.
- **`event.code` вместо `event.key`.** Выбор сделан для независимости от раскладки клавиатуры (кириллица/латиница не влияют на физические `ArrowLeft`/`Space`/`ControlLeft`) — стандартная практика для игр, риска не несёт, но стоит перепроверить вручную на нестандартных раскладках при `/implement`, если такая раскладка есть у `tester`.
- **`event.preventDefault()` на пробел.** Необходим, чтобы пробел не скроллил страницу — страница не скроллится (canvas на весь viewport, `000-project-bootstrap`), но стоит держать в голове, если в будущих фичах на странице появится скроллируемый контент вне canvas.
- **Vitest как новая зависимость.** Первое отклонение от «нулевых зависимостей сверх Vite/TypeScript» с `000-project-bootstrap`; обоснование — раздел Constitution Check выше. Риск минимален: Vitest — общепринятый стандарт для Vite-проектов, конфигурация тривиальна.
- **Каскадный порядок вычислений в `updateFrog` (старт прыжка → продолжение полёта в одном вызове).** Решение зафиксировано явно в §«`game/frog.ts`» п.2 после находки `reviewer` при `/analyze`: на кадре старта прыжка `jumpElapsedSeconds` по итогу вызова равен `deltaTimeSeconds`, а не `0`.
