description: Реализовать фичу по tasks.md — оркестрирует developer (по задачам, TDD) → tester (сверка acceptance criteria) → reviewer (gate перед финальным /commit)
argument-hint: [конкретные ID задач через запятую — необязательно, иначе все незакрытые]
---

**ID задач от пользователя (необязательно):** $ARGUMENTS

Это самая длинная и рискованная команда цикла — веди её по шагам явно, не сокращай.

## 0. Предусловия

1. Определи текущую ветку (`git branch --show-current`) — должна быть `feature/NNN-*`, совпадающая с `tasks.md`, который собираешься выполнять. Эта команда НЕ создаёт новую ветку — она уже создана в `/specify`.
2. Найди `specs/NNN-feature-name/{spec.md,plan.md,tasks.md}`. Если чего-то нет — сообщи, какой фазы не хватает, и останови выполнение.

## 1. Цикл developer (по задачам)

Для каждой незакрытой задачи в `tasks.md` (если заданы конкретные ID в `$ARGUMENTS` — только они, иначе все, в порядке зависимостей; **строго последовательно, даже для помеченных `[P]`** — параллельное исполнение не реализовано в этой версии):

1. Спавни subagent `developer` (Agent tool, `subagent_type: "developer"`, foreground) с самодостаточным prompt: конкретный `T00N` и текст задачи, связанный `AC-N` из `spec.md`, пути к `plan.md` и `.specify/memory/constitution.md`.
2. После завершения — прогони `git status`/`git diff --stat`, коротко проверь, что чек-бокс `T00N` в `tasks.md` отмечен и тесты, судя по выводу агента, зелёные.
3. `/commit` с аргументом «только закоммить, не мержи и не пушь».
4. Если `developer` остановился с вопросом (через `AskUserQuestion` он уже спросил пользователя напрямую) — дождись ответа и либо продолжи тот же вызов, либо перезапусти его с учётом ответа.

## 2. tester (после того как все задачи закрыты)

1. Спавни subagent `tester` (Agent tool, `subagent_type: "tester"`, foreground) с prompt: полный `spec.md` (все `AC-N`), путь к коду фичи.
2. Прочитай итоговую таблицу `AC-N` → статус.
   - Все `AC-N` пройдены → переходи к шагу 3.
   - Есть непройденные → покажи отчёт пользователю. Если проблема в коде — верни конкретную задачу `developer` на доработку (шаг 1 для этой одной задачи) и прогони `tester` заново. Если проблема в том, что `tasks.md` не покрывает `AC-N` вообще — сообщи пользователю, что нужен возврат к `/tasks`, и остановись (это не чинится внутри `/implement`).
   - **Ограничение:** не более 2 циклов «tester → доработка» подряд без участия пользователя. На третьем несовпадении — остановись и спроси пользователя явно, как поступить.
3. `/commit` с аргументом «только закоммить, не мержи и не пушь» (если tester что-то писал/менял).

## 3. reviewer (gate перед финальным `/commit`)

1. Спавни subagent `reviewer` (Agent tool, `subagent_type: "reviewer"`, foreground) с prompt: режим «код», диапазон диффа (от точки ветвления от `master` до текущего HEAD), пути к `spec.md`/`plan.md`/`constitution.md`.
2. `reviewer` вернёт находки через `ReportFindings`.
   - Пустой список → Definition of Done выполнено, переходи к шагу 4.
   - Есть находки → покажи их пользователю как есть (не исправляй молча). Спроси пользователя (`AskUserQuestion` в основном потоке): доработать (ещё один `developer`-раунд на конкретную находку + повторный `reviewer`, не более 2 циклов) / принять как есть с пометкой в `tasks.md` / остановиться. Без явного ответа пользователя — не двигайся дальше.

## 4. Definition of Done → финальный commit

Все три условия одновременно: все задачи `tasks.md` закрыты **и** `tester` подтвердил каждый `AC-N` **и** `reviewer` не имеет открытых находок (либо пользователь явно принял оставшиеся).

Только тогда — обычный `/commit` **без** аргумента «только закоммить»: мерж `feature/NNN-feature-name` в `master`, push, удаление ветки.
